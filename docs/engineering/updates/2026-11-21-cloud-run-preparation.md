## Implementation

`Dockerfile.cloud-run` uses the official Node 26.13.1 Bookworm slim digest `sha256:5df79989ed685e09f0a98019db4cebfb22fb9df1a53c0161664a011f7ff6b0f1`, resolved from the registry during this task. Its first stage builds the original-only frontend; the runtime installs only locked production dependencies and copies the existing handlers/transport and generated public files. It runs as the unprivileged node user and binds the injected port on all container interfaces. No service credentials or project-owner evidence enter the image. The Dockerfile-specific context allowlist omits legacy media before build as well as the existing artifact exclusion after build.

The image reuses unchanged MOVO API/accounting/authorization code and the existing Supabase project. Client storage, financial field formats, entitlement rules and app identity remain unchanged. No database is copied into container storage.

`render-cloud-run-service.cjs` produces a reviewable staging manifest locally. Inputs must name the actual project/region, matching runtime identity and regional immutable Artifact Registry image. Secret references use numeric versions; no secret values are read or emitted. Initial settings retain billing off, low concurrency, scale-to-zero/two maximum instances and process-health probes. The renderer does not grant public invocation, bypass app bearer/owner/MFA checks or contact Google APIs. Existing service IAM/traffic must still be inspected by the operator before applying a manifest.

`smoke-cloud-run-container.cjs` starts only the locally built image with dropped capabilities, no new privileges, a read-only filesystem and a non-default injected port. It checks a non-loopback container interface, non-root identity, frontend/notices, auth/billing denial and private/legacy asset exclusions, then removes its own test container. The dedicated GitHub workflow builds and runs this without cloud credentials or publishing. [Deployment inputs, instructions and limits](../../CLOUD_RUN_DEPLOYMENT.md).
