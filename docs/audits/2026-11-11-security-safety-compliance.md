**11 November 2026, Philippine time · Release decision: NO-GO for broader public rollout or paid launch.**

Scope: MOVO (Money Organizer & Visual Outflow), public web deployment, live Supabase authorization metadata, Android release evidence, iOS source and release branch, and Philippine, Apple, and Google Play requirements. Repository main and the latest READY production deployment both identify commit `166dbd1271fc21bde29025be93f321c205c7566b`. Production checks used public HTTP requests and read-only database catalog queries. No customer records, secret values, payments, deployments, or schema changes were involved. No critical exposure or active breach was established by the checks performed.

## Release blockers

### 1. High — Direct transaction writes bypass ledger safeguards
**Confirmed in the live grants, policies, and triggers.** The authenticated role retains UPDATE and DELETE on its own `transactions` rows. The row-level policies check the owner, while the live table triggers enforce plan eligibility, allocation reconciliation, and timestamps. They do not enforce the hybrid RPC's revision check, linked-payment edit restrictions, or complete deletion-and-reversal path. For example, the live bill-payment foreign key sets its transaction reference to NULL on deletion. A direct delete can therefore remove the underlying transaction without reversing the active payment. Direct UPDATE can also bypass the RPC's exact-cent bounds and immutable transaction metadata checks.

The demonstrated authorization gap applies to eligible users' own rows. Live composite foreign keys enforce account and transfer-destination ownership. A separate schedule reference uses a single-column FK, while only the hybrid RPC verifies the schedule owner. This allows a foreign schedule ID to be referenced if a caller already knows it, subject to other checks. The catalog evidence does not establish cross-user data retrieval or arbitrary edits to another tenant.

Close raw mutation paths where supported clients have migrated, or enforce equivalent ownership and accounting invariants at the database boundary. Inventory legacy callers first. Test competing writes, wrong-owner IDs, direct REST mutations, payment reversal, duplicate retries, offline replay and exact-cent balances with synthetic data.

### 2. High — Delete Account is hidden when Cloud Sync is off
**Confirmed in source.** Settings renders Delete Account only when `cloudMode` is true. A signed-in account can be in local mode with Cloud Sync disabled or in a device-copy state. The public deletion page tells people to sign in and use a Settings path that can be unavailable. It provides a support email fallback. Apple requires in-app initiation and Google requires both an in-app option and an external request path.

The API verifies the Supabase user and limits deletion to that account, but a valid bearer and static confirmation are sufficient. It removes receipt/QR objects and transactions before the Auth user. An intermediate failure can leave a partially deleted account. The client also reports a generic deletion failure if IndexedDB cleanup fails after the server has deleted the account, and suppresses some local cleanup errors. Prior owner-audit FK blockers have been fixed in the live catalog.

Show deletion for every signed-in account regardless of plan or sync mode. Use a retryable deletion flow with a distinct account-deleted/device-cleanup result, and assess fresh authentication for the destructive endpoint. Verify free, expired and cloud-disabled accounts, active subscriptions, upload/delete concurrency, partial failures, processor retention and device cleanup with disposable accounts.

### 3. High — Google Play cancellation can end paid access early
**Confirmed in the verification code and live entitlement rules.** The verifier maps `SUBSCRIPTION_STATE_CANCELED` to `expired` regardless of the reported expiry time. Production access requires status `active` or `grace_period` and a future expiry. When that cancellation state is committed, access can end before the period the user paid for. Google specifies continued access through the applicable expiry after ordinary cancellation. Refund, revocation, pending cancellation, and expiry have distinct effects.

Keep access through the verified expiry on ordinary cancellation, and prove cancel, expire, renew, restore, refund, revoke and out-of-order notification behavior in an isolated billing environment. No paid purchase or cancellation was performed in this audit.

[Google verifier](https://github.com/nasrinaiv0/movo/blob/166dbd1271fc21bde29025be93f321c205c7566b/api/lib/purchaseVerification.js#L152) · [Google subscription lifecycle](https://developer.android.com/google/play/billing/lifecycle/subscriptions)

### 4. High before monetization — Billing and purchase metadata are incomplete
Both live platform configuration responses returned `enabled:false`. Production configuration did not list `GOOGLE_PLAY_RTDN_SUBSCRIPTION`, which Google notification handling and readiness require. The Play product-ID environment names are present but the verification code reads the shared product catalog. Actual Play Console product IDs, base plans, prices, and active track were unavailable. The Google service account is now marked sensitive in production, resolving the prior readable-secret finding.

The configuration flag is enforced in the public config handler. The authenticated verify endpoint still attempts store verification and entitlement writes independently. Decide explicitly which operations the flag is meant to disable, preserving lifecycle processing for existing customers where appropriate. The production Google verifier rejects test purchases, so use isolated billing configuration and entitlement data for license-testing. The current billing implementation includes store authenticity and account-binding checks, request limits on purchase verification, and notification replay controls. These were reviewed in code without a store transaction.

## Verified controls and changes since the prior audit

- The production hybrid sync operation table and RPC exist, and the four previously blocking owner references now use ON DELETE SET NULL. The live immutability trigger includes an exception for anonymization after user deletion. Authenticated hybrid functionality and actual deletion still require test execution.
- All 44 public base tables have RLS enabled. Receipt and QR buckets are private, have upload constraints, and use authenticated user-prefix policies. The 15 policyless RLS tables are default-deny under ordinary RLS behavior. The advisor flagged 15 authenticated-callable SECURITY DEFINER functions and disabled leaked-password protection. No public-schema SECURITY DEFINER was executable by the anonymous role in the inspected catalog. Verify all privileged entry points using two synthetic tenants, and confirm which password-based routes are enabled before assigning impact to the password warning.
- Production home, Privacy Policy, Terms, and the published account-deletion page were reachable. Live responses included CSP, HSTS, nosniff and frame denial. The CSP allows all HTTPS/WSS connection destinations. Narrow the allowlist after mapping the necessary providers. Anonymous requests to the correct entitlement, owner and AI API paths returned HTTP 401. These probes establish unauthenticated rejection for those routes.
- `npm audit --omit=dev` reported zero known npm production advisories. The full lockfile audit reported 34 findings (13 high, 5 moderate, 16 low), with the direct advisory rooted in the development build dependency `react-scripts`. Assess CI exposure and upgrades without force-installing a breaking dependency. Separate native dependency and repository-history secret scans were outside the evidence collected.
- The prior 1,000-row ledger cap is addressed in source by explicit pagination. FX conversion returns NaN for missing/invalid cross-currency rates and includes a stale-rate helper. Estimated fallback rates remain available. Verify concurrent pagination and stale-rate treatment across the balance, reports, imports and transfers.
- Android signed AAB run `42965924372` succeeded on the audited commit and uploaded the unexpired `movo-google-play-aab-15` artifact. Steps reported successful configuration checks, web asset build, native asset sync, signing and bundle creation. The signed file was not downloaded, reverified, or installed. The available iOS release-hardening branch `a7c91783` is separate from the audited production commit.

## Verification still required

Vercel Sandbox rejected sandbox creation for MOVO with HTTP 402 `payment_required`. No authenticated Vercel/Sandbox CLI fallback was available. Fresh browser UI, authenticated workflows, two-tenant isolation, accounting simulation and adversarial billing execution were therefore unverified. The live HTTP probes, catalog results, source inspection, npm advisory checks and reported GitHub build outcomes are separate evidence.

1. Close the database ledger bypass and make deletion available to all signed-in account states. Verify both with synthetic accounts and disposable records.
2. Reconcile privacy disclosures and retention behavior. Gather controller, DPO, NPC applicability, processor, consumer-redress and store declaration evidence.
3. Correct Google cancellation and complete Play configuration. Run the full verified purchase lifecycle before enabling paid sales.
4. Restore MOVO's Vercel Sandbox access. Test narrow-screen UI, OTP and OAuth, account deletion, cloud writes and retries, offline handoff, receipts/QR, CSV import/export, voice, and user/device isolation.
5. Validate the exact signed Android and iOS builds on physical devices and reconcile findings with the actual store submissions.
